01

Three different things called "private"

This collision caused most of the confusion on Day 1. The three are unrelated. Separate them and the rest falls into place.

The thingWhat it meansWho decides it
0.0.0.0/0Every address that exists. A range — not public, not private, but all.Nobody. It is arithmetic.
A private IP range
10.x.x.x		An address the public internet refuses to route.A worldwide standard, RFC 1918.
A private subnetA subnet whose route table has no internet-gateway route.You, in the route table.
The line to hold

0.0.0.0/0 is the destination side of a route rule. It never makes anything public. The internet gateway on the right-hand side does.

02

Reading a CIDR block

An IP address is 32 bits, written as four chunks of 8. Each chunk is an octet, 0–255. The number after the slash says how many bits are locked.

   10   .    0     .    1     .   47
00001010 . 00000000 . 00000001 . 00101111
|________________________|
   the first 24 bits are locked        the last 8 are free

/24 means every address that starts with 10.0.1. That is the whole idea. A bigger prefix locks more, so it leaves fewer addresses.

Addresses = 2(32 − prefix)

PrefixOctets lockedFree to changeAddresses
/810.last 3 octets16,777,216
/1610.0.last 2 octets65,536
/2410.0.1.last octet256
/3210.0.1.47nothing1

The four-step range recipe

When the prefix is not a multiple of 8, run this. It always works.

  1. How many addresses? 2(32 − prefix)
  2. Which octet moves? /1–/8 the first · /9–/16 the second · /17–/24 the third · /25–/32 the fourth
  3. What is the step in that octet? 2(bits free in that octet). Blocks start at multiples of the step.
  4. Last address = first + size − 1. Not first + size.

Worked · 192.168.1.0/25

32 − 25 = 7 free bits          -> 128 addresses
/25 falls in the 4th octet     -> the last octet moves
25 − 24 = 1 bit locked there   -> step = 2^7 = 128

192.168.1.0/25    =  192.168.1.0   ... 192.168.1.127
192.168.1.128/25  =  192.168.1.128 ... 192.168.1.255
Live error

10.0.5.64/26 runs .65 to .129

Correct

10.0.5.64/26 runs .64 to .127

Two slips at once. The block starts at the number in the CIDR, so the first address is .64, not .65. And the first address counts, so 64 addresses from 64 end at 127 — .128 is where the next block begins.

Splitting a range

The rule

To split into 2n equal parts, add n to the prefix. Two parts → +1. Four parts → +2. Eight parts → +3.

Live error

Divide the free bits: 16 ÷ 4 = 4

Correct

Add to the prefix: /16 + 2 = /18, four times

Dividing the bits produced /20 /24 /28 /32 — four different sizes, all starting at the same address, so they sat on top of one another. Four equal parts must be four blocks of the same prefix.
10.0.0.0/16 split four ways
32 − 18 = 14 free bits -> 16,384 addresses each
/18 sits in the 3rd octet; 2 bits locked there -> step 64

10.0.0.0/18      10.0.0.0    ... 10.0.63.255
10.0.64.0/18     10.0.64.0   ... 10.0.127.255
10.0.128.0/18    10.0.128.0  ... 10.0.191.255
10.0.192.0/18    10.0.192.0  ... 10.0.255.255
Live error

“16384 / 256 = 64 usable addresses”

Correct

16,384 addresses each. 64 is the step in the third octet.

Both numbers come out of the same division, but one is a count and the other is a stride — how far apart the blocks start. Keep them apart.

Which ranges are private

RangeCoversSize
10.0.0.0/810. anything16.7M
172.16.0.0/12172.16.x through 172.31.x — only .16 to .311M
192.168.0.0/16192.168. anything65K
Everything else is public. 34.120.55.10 is public. 8.8.8.8 is public.

The 172 range is the trap: 172.15.0.1 and 172.32.0.1 are both public. And “starts with 192” is not enough — 192.168.4.4 is private, 192.169.4.4 is public.

AWS reserves 5 per subnet

A /24 gives 256 addresses but only 251 usable: the network address, the VPC router, DNS, one held for future use, and broadcast. So a /26 holds 64 − 5 = 59 — which does not fit 60 servers. Always subtract the five, and always leave slack: a subnet CIDR cannot be changed later.

03

The five boxes

BoxAttached toWhat it is
VPCa regionYour own private slice of the AWS network. It has a CIDR.
Subnetexactly 1 AZA slice of the VPC range. Its CIDR and its AZ both matter.
Route tablea subnetA list of rules. Answers “which way out?”
Internet gatewaythe VPCThe door to the internet. One per VPC.
NAT gatewaya public subnetLets private subnets call out. Nothing may call in.

What a route table actually does

It is not a directory. It never knows where any server lives. It answers one question: I hold a packet, its destination is X, where do I send it?

ROUTE TABLE rt-private
  10.0.0.0/16   ->  local      # my own VPC
  0.0.0.0/0     ->  nat-abc    # the "else" branch

read as code:
  if dest in 10.0.0.0/16:  send local
  else:                    send to the NAT
  • The most specific match wins. /24 beats /16 beats /0.
  • Every subnet has exactly one route table. Attach none and it uses the VPC's main one.
  • AWS adds 10.0.0.0/16 -> local and you cannot remove it. So every subnet in a VPC can already reach every other.
  • local does not mean "private subnet". It means "the destination is inside this VPC — deliver it directly, use no gateway". Public subnets carry the same line.
Why the local route covers the whole VPC

If rt-private said 10.0.128.0/18 -> local, then private-a could not reach private-b, and an app server could not reach a database in the other AZ. The local route must span the entire VPC for cross-AZ traffic to work at all.

The definition of public

No checkbox exists

A subnet is public if its route table contains 0.0.0.0/0 -> igw-xxxx. That is the entire definition.

Which is exactly why you cannot solve the outbound problem by adding an IGW route to a private subnet — that makes it public. You need the NAT gateway instead.

What the NAT gateway does

  1. The private server sends its packet to the NAT gateway.
  2. The NAT swaps the source address for its own public IP, and sends it out through the IGW.
  3. The far end replies to the NAT gateway.
  4. The NAT remembers who asked, and passes the reply back inside.
Live error

0.0.0.0/0 -> NAT  (internet inbound)

Correct

0.0.0.0/0 -> NAT  (outbound only)

A NAT gateway is outbound only, and that asymmetry is the entire purpose of a private subnet. It returns replies to calls that started inside. Nothing on the internet can start a connection through it.
NAT placementCostIf that AZ fails
One, shared~$32 / monthThe other AZ loses all outbound traffic.
One per AZ~$64 / monthThe other AZ is unaffected.

Plus roughly $0.045 per GB processed. Saying this tradeoff out loud is cost-versus-resilience reasoning, and it earns marks in the case study.

04

What a packet is, and who reads which layer

Bytes on a wire. Your JSON is only the innermost part. Each layer adds a header in front and hands the result down.

┌─ Ethernet header ─────────────────────────────────┐
│ ┌─ IP header ───────────────────────────────────┐ │
│ │  src 10.0.11.20   dst 34.120.55.10            │ │   <- route table reads here
│ │ ┌─ TCP header ──────────────────────────────┐ │ │
│ │ │  src port 51234   dst port 443            │ │ │   <- security group reads here
│ │ │ ┌─ HTTP ────────────────────────────────┐ │ │ │
│ │ │ │  POST /v1/charges                     │ │ │ │   <- load balancer reads here
│ │ │ │  {"amount": 500}   <- your JSON        │ │ │ │
│ │ │ └───────────────────────────────────────┘ │ │ │
│ │ └───────────────────────────────────────────┘ │ │
│ └───────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────┘

A route table cannot see the port, let alone the JSON. It reads one field. That is why a route table is never the thing blocking port 443.

A packet carries about 1500 bytes. A 50 KB response is roughly 35 packets, which TCP puts back in order at the far end.

ProtocolLayerPortWhat it gives you
IP3—Addresses. No guarantee of delivery.
TCP4—A connection. Ordered, retried, guaranteed. Slow to start.
UDP4—Fire and forget. No order, no retry. Fast.
HTTP780Requests over TCP. HyperText Transfer Protocol.
HTTPS7443HTTP inside TLS encryption.
SSH722An encrypted shell, over TCP.
DNS753Name to IP. Normally over UDP.

Why DNS picks UDP: one small question, one small answer. A TCP connection spends three packets on a handshake before any data moves — more than a retry would cost. Video calls choose UDP for the same reason: a late frame is worthless, so do not retry it.

05

Security groups

A firewall attached to a resource — an instance, a load balancer, a database — never to a subnet.

  1. The default denies all inbound and allows all outbound. A new instance can call out; nothing reaches in.
  2. Allow rules only. There is no deny rule. To block one specific IP you need a network ACL — stateless, attached to the subnet, and it does have deny rules.
  3. A source can be another security group. from sg-alb beats a hardcoded IP, because instances come and go.
  4. It is stateful. A reply to an allowed request needs no outbound rule — the group remembers the connection. So you write rules only for who starts the conversation.
Route tableSecurity group
Attached toa subneta resource
Readsdestination IPIP + port + protocol
Answers“which way out?”“may these two talk at all?”
Rule typesroutes onlyallow only
Remembers connectionsn/ayes — stateful
Both must pass

A correct route with a closed security group is dropped. An open security group with no route never leaves. When something cannot connect in AWS, check this pair first.

The chain to memorise

sg-alb        IN:  TCP 443   from 0.0.0.0/0
              OUT: TCP 8080  to sg-app

sg-app        IN:  TCP 8080  from sg-alb
              OUT: (default allow all)

sg-database   IN:  TCP 5432  from sg-app
              OUT: (nothing needed)

The internet reaches only the load balancer. The load balancer reaches only the app. The app reaches only the database. Nothing on the internet can reach the database even by mistake, because no rule names it.

06

How the internet reaches a server

Your instance holds 10.0.1.20 — an address the internet refuses to route. So AWS gives it a second address, held by the gateway rather than by the machine.

instance   private IP  10.0.1.20     <- the OS only ever sees this one
           public  IP  54.12.33.9    <- held by the IGW, not by the OS
  1. DNS resolves myapp.com to 54.12.33.9.
  2. The browser sends the packet there. The internet routes it to the IGW.
  3. The IGW rewrites the destination to 10.0.1.20 and passes it in.
  4. On the way back, the IGW rewrites the source to 54.12.33.9.

Run ifconfig on that server and you see only 10.0.1.20. The machine never knows it has a public address. An Elastic IP is the same mechanism, except you own the number and it survives a stop/start; a plain public IP does not.

The four conditions — a troubleshooting order

  1. The subnet's route table has 0.0.0.0/0 -> igw.
  2. The instance has a public IP or an Elastic IP.
  3. Its security group allows inbound on that port.
  4. The network ACL allows it (the default allows everything).
Why the order matters

Miss any one and it fails silently — no error, just a timeout. Walk the list in this order out loud and you have shown a method rather than a guess.

The request path

Inbound browser→ DNS → 54.12.33.9→ IGW→ ALB :443→ app :8080→ RDS primary :5432
Return — every hop is stateful, so no extra rule is needed RDS→ app→ ALB→ IGW rewrites source→ browser

Note what is not in that path: the NAT gateway. It carries no inbound traffic at all. It appears only when the app server calls out — to a payment API, or to fetch a package.
