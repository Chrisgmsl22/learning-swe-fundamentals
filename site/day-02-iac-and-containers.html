The three IaC tools

The official guide names all three. They are not competitors — two of them do one job and the third does a different one.

The sentence to say

Terraform and CloudFormation build the house. Ansible furnishes it. The first two provision infrastructure. Ansible does configuration management — it sets up what runs inside a machine that already exists.

TerraformCloudFormationAnsible

Terraform or Ansible?

Not a choice — different jobs. Terraform builds the VPC, the subnets and the instances. Ansible then installs nginx on those instances and writes their config. Ansible can create cloud resources, but it has no state file, no plan and no destroy, so Terraform is the better provisioner.

Terraform or CloudFormation?

Terraform when you have more than one provider, or want modules and loops — it is the industry default and HCL reads more easily. CloudFormation when it is AWS-only and you want AWS to own the state and the rollback. Both are declarative: you describe the end state, not the steps.

The four real differences

  1. No loops. Four subnets means four blocks. This is why CloudFormation templates get long.
  2. Nested things become separate resources. A route is a block inside aws_route_table in Terraform; AWS::EC2::Route is its own resource here. Same for the IGW attachment.
  3. Different property names for the same idea. A security group takes cidr_blocks (a list) in Terraform and CidrIp (one value) in CloudFormation. Expect this trap live.
  4. State. Terraform keeps a file you must store and protect. CloudFormation keeps the stack inside AWS. That is its single best argument.

When to write DependsOn

Both tools build the order from the references you write. You need DependsOn only when a dependency is real but invisible.

PublicDefaultRoute  --> !Ref InternetGateway
   the reference says "the IGW must exist".
   It does NOT say "the IGW must be ATTACHED to the VPC".
   That resource is never named here -> invisible -> state it.

PrivateDefaultRoute --> !Ref NatGateway --> !GetAtt NatEip --> DependsOn: IgwAttachment
   every link is written down -> visible -> say nothing.
The rule

Add DependsOn only when the ordering cannot be seen in a reference. Adding it everywhere is a smell — it means you did not trust the graph, and it serialises a build that could have run in parallel.

Live error

"The private route table does not rely on the outside world, it is simply internal."

Correct

It depends on the outside world completely — it points at the NAT, and a NAT is useless without the IGW.

Private does not mean disconnected. It means outbound only. The reason no DependsOn is needed there is that the chain is already written down, not that the dependency is absent.

Route table · route · association

Three separate objects, and the split trips people constantly.

ObjectWhat it isAnalogy
RouteTableAn empty container of rules. Belongs to the VPC.A blank signpost
RouteOne rule: 0.0.0.0/0 → somewhereThe directions painted on it
SubnetRouteTableAssociationAttaches the table to a subnetPlanting it at a junction
Why this is a nasty bug

Without the association nothing happens. The table exists, the rules are perfect, and no packet ever consults it — the subnet quietly falls back to the VPC's main route table instead. Everything looks right.

03

Ansible

Agentless. It installs nothing on the target — it connects over SSH port 22, runs Python there, and disconnects. Close port 22 and Ansible can do nothing.

WordMeaning
InventoryThe list of target machines, in groups.
PlaybookA YAML file of plays. Each maps a host group to a list of tasks.
TaskOne step. It calls a module.
ModuleThe unit that does the work — package, service, file, template. Modules are what make Ansible idempotent.
HandlerRuns at the end, once, and only if a task notified it.
RoleA reusable folder of tasks and templates. Ansible's answer to a Terraform module.
 
- name: Install nginx
  ansible.builtin.package:
    name: nginx
    state: present          # the END STATE, not "install"

- name: Write the config from a template
  ansible.builtin.template:
    src: nginx.conf.j2
    dest: /etc/nginx/nginx.conf
    mode: "0644"
  notify: Reload nginx      # fires ONLY if the file actually changed

Idempotent is the word to know. Every module checks the machine before it acts. Run the playbook 10 times and it ends in the same condition — runs 2 to 10 report ok rather than changed.

Terraform describes a destination. Ansible describes a journey.

Easier: you can express steps with no data dependency that still must run in order — stop the service, swap the binary, start the service. Terraform sees no references between those, so it would run them at once. A procedure cannot be expressed as a graph.

Harder: you own the correctness. Swap two tasks and it breaks silently, with no graph to catch it. You also lose automatic parallelism, a real preview of the end state, and destroy.

Reaching a private server

Ansible needs SSH. Your app servers sit in private subnets, so three of the four reachability conditions fail — no IGW route, no public IP, and port 22 closed. Opening port 22 alone changes nothing, because a NAT carries no inbound traffic.

OptionHowCost
SSM Session ManagerThe agent calls out through the NAT. No inbound port at all.Free. Lead with this.
Bastion hostA small instance in a public subnet. SSH 22 from your IP only; the app SG allows 22 from the bastion's SG.One instance to patch.
Control node inside the VPCRun Ansible from a machine already in a private subnet.Nothing exposed.
04

File permissions

Four octal digits. Most people only ever read the last three.

0 7 5 0
│ │ │ └── others   0 = ---
│ │ └──── group    5 = r-x
│ └────── owner    7 = rwx
└──────── SPECIAL BITS

read = 4    write = 2    execute = 1        7 = 4+2+1
Special bitValueWhat it does
setuid4The file runs as its owner, not as you.
setgid2On a directory: new files inherit the group.
sticky1In a shared directory, only the owner may delete their own file. /tmp is 1777.
Live error

The leading 0 is the file type — - for a file.

Correct

The leading digit is the special bits. 0 means none are set.

The file type is a separate thing, shown by ls -l as the first of ten characters — -rwxr-x--- a file, drwxr-xr-x a directory, lrwxrwxrwx a symlink. It is never part of the number, and chmod cannot change it.
The ones worth knowing on sight

600 a private key — owner read/write, nobody else. SSH refuses a key that is more open than this.
644 a normal config file — everyone reads, owner writes.
755 a script or a directory — everyone runs or enters, owner writes.
777 never. It is the answer to "I do not know which permission it needs".

Docker

An image is a stack of read-only layers. A container is that stack plus one writable layer on top. Every instruction that changes the filesystem makes one layer.

The cache rule — the whole optimisation game

Docker walks the file top to bottom and reuses a cached layer when its inputs are unchanged. The first instruction that changes invalidates that layer and every layer below it. So order instructions from least likely to change to most likely.

The eight fixes

ProblemFixWhy
FROM python:3.12python:3.12-slim~1 GB of the size, in one line. Never latest.
COPY . . before pip installCopy requirements.txt only, install, then copy the sourceOne character of Python otherwise reinstalls every dependency. This is the CI complaint.
Four RUN apt-get linesOne RUN, with rm -rf /var/lib/apt/lists/* in the same layerA layer is a snapshot. Deleting later only hides the bytes; the image still carries them.
curl, vim, build-essentialDelete themAttack surface and CVE noise. Containers are immutable — you never edit one, you replace it.
No USERuseradd, then USER appuser before CMDA container escape as root is far worse than as appuser.
No .dockerignoreExclude .git, .env, venv, cachesThe whole context is uploaded before the build. And COPY . . otherwise ships .env and full git history into the image.
pip installadd --no-cache-dirpip's download cache is baked into the layer and never used again.
CMD python app/main.pyCMD ["gunicorn", ...]See below. This one is worth real marks.

PID 1 and why exec form matters

PID 1 is the first process, the root of the process tree. Inside a container that is your application. Two things make it special: when PID 1 exits the container is finished, and the kernel does not apply default signal handling to PID 1 — a signal is dropped unless the program handles it.

SHELL FORM   CMD python app/main.py        EXEC FORM   CMD ["python","app/main.py"]
  PID  PPID COMMAND                          PID  PPID COMMAND
    1     0 sh        <- PID 1                 1     0 python    <- your app
    7     1 sh
    9     7 python    <- your app

Docker and Kubernetes stop a container the same way: send SIGTERM to PID 1, wait (10 s for Docker, 30 s for Kubernetes), then send SIGKILL, which cannot be caught.

In shell form the signal goes to sh, and sh -c does not forward it. Your app never hears anything and gets killed mid-request. Every rolling deploy drops in-flight connections, and the app logs nothing, because it was never told.

Say this on Thursday

"Exec form, so the app is PID 1 and receives SIGTERM — otherwise every rolling deploy drops in-flight requests." That is a Docker answer, a Kubernetes answer and a failure-modes answer at once.
