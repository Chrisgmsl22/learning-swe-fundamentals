02.01

APIs

An application programming interface is a contract between software components. It defines requests, results, and errors.

  • Gain: Clients use shared behavior without direct database access.
  • Limit: Contract changes can break clients. An API can also exist within one process.

02.02

REST

REST is an architectural style for resource interfaces. Resources have identifiers, and each request carries the context that the server needs.

  • Gain: Consistent resource interfaces help clients use standard HTTP behavior.
  • Limit: JSON over HTTP alone does not make an API RESTful. This sketch omits other REST constraints.

Roy Fielding: REST constraints · Mermaid source

02.03

GraphQL

GraphQL defines a typed schema and a query language. A client names the fields it needs in its request.

  • Gain: A client can request related fields through one interface.
  • Limit: One client request can cause many database queries. The schema does not guarantee cheap execution.

GraphQL: Official introduction · Mermaid source

02.04

WebSockets

A WebSocket connection stays open so a client and a server can both send messages without a new HTTP request per message.

  • Gain: The server can send updates as soon as an event occurs.
  • Limit: The service must handle connection loss, reconnects, and slow clients.

MDN: WebSocket API · Mermaid source

02.05

Webhooks

A webhook is an HTTP request that one service sends to another when an event occurs.

  • Gain: The recipient receives event notices without repeated status requests.
  • Limit: Delivery can repeat or arrive out of order. The sender retries delivery. The receiver must handle duplicate events.

Stripe: Webhook delivery and duplicate events · Mermaid source

02.06

API gateway

An API gateway is a common entry point that routes requests to services. It can also apply shared access rules.

  • Gain: Clients use one public entry point across several services.
  • Limit: The gateway adds latency and needs its own capacity and failure plan.

AWS: API gateway responsibilities · Mermaid source

02.07

Rate limiting

A rate limit caps requests for an identity within a time period. The identity can be a user, account, or address.

  • Gain: A limit reduces abuse and protects some service capacity.
  • Limit: A per-user limit alone cannot control total demand. Legitimate requests can also exceed a limit.

MDN: HTTP 429 · Mermaid source

02.08

Idempotency

An operation is idempotent when repeated equivalent requests have the same intended effect as one request.

  • Gain: The client can retry after an uncertain response without a second order.
  • Limit: The server must enforce the key contract and retention period. A header alone cannot prevent duplicate effects.
