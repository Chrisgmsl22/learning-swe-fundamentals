06 · Design and operations

How do we justify and operate the design?

A useful design starts with user needs. Estimates, measurements, access rules, and costs turn its boxes into an operational plan.

Each diagram isolates one concept. A box describes a responsibility; it does not always require a separate machine.

06.01

Requirements and scope

Requirements state what users need and which service qualities matter. Scope states which features the current design includes.

  • Gain: A clear boundary lets you design and test the required paths first.
  • Limit: A small diagram does not specify speed or reliability. Add measurable targets and an explicit list of excluded features.

06.02

Estimates and assumptions

An estimate predicts demand from explicit assumptions. It helps expose a possible capacity limit before you choose resources.

  • Gain: A rough model reveals which component needs a capacity check.
  • Limit: These numbers are assumptions, not measurements. Average demand hides peaks, and resource capacity needs a representative load test.

06.03

Operations: metrics, logs, and alerts

Metrics summarize behavior as numbers. Logs record events. Alerts notify an operator when a condition needs action.

  • Gain: User-visible error and latency signals help detect faults and support diagnosis.
  • Limit: Too many alerts hide urgent faults. An alert should call for a clear action; CPU use alone does not prove successful redirects.

06.04

Security and abuse

Security controls restrict access to allowed actions. Abuse controls limit harmful use, including excessive requests and unsafe destination URLs.

  • Gain: Checks protect user data, service capacity, and people who follow links.
  • Limit: HTTPS protects data in transit; it does not prove that a user may edit a link or that its destination is safe.

06.05

Cost and capacity

Capacity is the work a system can support under stated targets. Cost includes compute, storage, network traffic, and operational work.

  • Gain: Capacity reserves can absorb a fault or demand burst.
  • Limit: Idle reserves cost money. Two servers help only if the survivor and database can handle the required demand. Measure before you resize.
