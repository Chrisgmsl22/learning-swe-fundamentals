05 · Distribution and failures

How do copies and separate services behave?

Separate machines can fail or lose contact. Data copies, data splits, and recovery rules solve different problems.

05.01

Replication

Replication maintains copies of the same data. This example sends changes from a primary database to a replica.

  • Gain: A replica can support extra reads and provide another copy after some failures.
  • Limit: An asynchronous replica can lag behind the primary. Replication does not replace backups; an accidental delete can reach every replica.

05.02

Sharding

Sharding divides records across separate database servers. Each shard owns a subset of records, rather than a full copy.

  • Gain: Several servers can share data size and query demand.
  • Limit: A poor key can concentrate demand on one shard. Cross-shard queries and later data moves add complexity.

05.03

Vertical partitioning

Vertical partitioning separates fields or functional parts of data. Here, the short code connects URL fields with optional preview fields.

  • Gain: The frequent redirect path avoids large fields that it does not need.
  • Limit: A request that needs both parts must combine results. Separate stores need explicit rules for related updates.

05.04

CAP

CAP concerns a network partition: nodes cannot exchange messages. A distributed store cannot guarantee both consistent reads and availability throughout that partition.

  • Gain: A consistency-first policy protects one current view. An availability-first policy preserves responses on both reachable sides.
  • Limit: Consistency-first can reject or delay requests. Availability-first can return stale data. CAP is not a free choice of any two letters.

Gilbert and Lynch: CAP proof · Mermaid source

Here, consistency means that reads respect one up-to-date order of operations. Availability means every request to a non-failed node eventually receives a successful response.

05.05

Microservices

Microservices split an application into separate services with clear responsibilities. Each service can deploy independently and owns its data.

  • Gain: Teams can change and scale each service independently.
  • Limit: Network calls add delay and failure cases. Separate services require explicit data contracts and more operational work.

Azure: microservices architecture · Mermaid source

05.06

Failure behavior and recovery

A failure plan defines timeouts, fallback paths, and recovery steps. A timeout limits how long a component waits for another component.

  • Gain: A failed optional cache does not have to stop all redirects.
  • Limit: The database must absorb extra traffic. Retries need limits and delays; repeated writes need protection against duplicate effects.
