## What the learner explained

- A cache hit supplies the destination URL.
- A cache miss leads to a database lookup and a cache update.
- An unknown short code can return 404.
- A cache failure differs from a cache miss.
- A cache supports a read-heavy service with fast lookups.
- Database fallback can serve requests during a cache outage.
- Multiple cache nodes could improve availability.
- Capacity pressure and regional failure are possible failure causes.
- Metrics could warn of some problems before an outage.

## Mentor explanations and corrections

| Question or proposal | Explanation |
| --- | --- |
| How does the browser redirect? | The shortener returns a redirect status and Location. The browser makes a new request to the destination. |
| Who serves the article? | The destination serves the content. The shortener owns URL resolution and the redirect response. |
| What if the destination is down? | The browser or destination supplies the error. The shortener cannot replace that response after navigation. |
| Does the gateway own cache fallback? | The URL retriever calls the cache and owns the database fallback. |
| Can another cache node serve the request? | Possibly. Data placement and replication determine whether that node has the key. |
| Can a timeout prove a cache outage? | No. It means the service did not receive a response within its allowed wait. |
| Is a two-second cache timeout quick? | It exceeds a hypothetical 200 ms redirect target before the database fallback even starts. |
| Does a full cache necessarily crash? | No. Depending on configuration, it can evict entries or reject writes. Memory exhaustion can still cause failure. |
| Does fallback survive a regional outage? | Only if the fallback dependencies remain available. A database in the same failed region cannot serve the request. |
| Can metrics prevent every outage? | No. They can reveal memory pressure, errors, or latency, but cannot guarantee advance notice. |

Example assumptions: 320 reads/second and a 95% cache hit rate.
Database traffic rises from about 16 to 320 reads/second when the cache becomes unavailable.
This arithmetic does not prove that the database can sustain that load.

Illustrative latency budget: 200 ms total, with a 20 ms cache timeout.
These are design assumptions, not measured performance or a selected production configuration.
