## Learner evidence

- A DNS resolution failure prevents the request from reaching the URL retriever.
- The application server owns the route and controller. The gateway applies security rules and forwards requests.
- The gateway can report an upstream connection failure to the client.
- A short timeout can reject a request from a healthy but slow server.
- After a worked example, the learner explained that cache time is one part of the complete redirect budget.
- Given a cache response time of 25 ms and a timeout of 20 ms, the learner predicted database fallback and extra database load.

## Mentor corrections

- A packet contains a header and data. A bit is the smallest binary unit.
- DNS resolves the hostname. The browser sends the path in its HTTP request; the path need not identify a directory.
- A failed connection does not prove that the server is down. Network faults and firewall rules can prevent access.
- A shorter timeout gives an earlier error or fallback; it does not speed up successful work.
- The 200 ms redirect target covers the complete request. It is not a required cache response duration.
- A cache timeout can trigger database fallback while the complete redirect still meets its target.
- More database traffic does not necessarily cause overload. Capacity determines whether that traffic causes overload.
- A timed-out operation may continue unless cancellation stops it.

The 200 ms redirect target, 20 ms cache timeout, and example response times were mentor assumptions, not measurements or learner-selected settings.
The learner initially confused the overall target with the cache timeout. Later explanations showed the distinction and fallback-load consequence.
The learner has not yet written a timeout-selection rule or justified a specific timeout from measurements and database capacity.
